Project Overview

NexusAI Dashboard started as a consulting engagement with a Series B logistics company that was drowning in operational data spread across six different BI tools. The ask was simple: consolidate everything into one real-time platform and add AI to surface actionable insights automatically.

Eighteen months later the platform processes over 10 million events per day, serves 500+ enterprise customers, and has shipped three major feature releases including an AI co-pilot that generates natural-language summaries of anomalies as they happen.

"NexusAI completely replaced our data team's morning report ritual. The AI summaries land in Slack at 7am before anyone opens a laptop."

The Problem

The client was running six separate dashboards — Grafana, Metabase, a custom React app, and three vendor portals. Their data team spent 2–3 hours every morning manually stitching together reports. Alerts were firing but nobody could correlate them fast enough to act.

  • Alert fatigue: 400+ daily alerts across tools, most duplicates
  • Data lag: dashboards refreshed every 15 minutes, not real-time
  • No unified view: cross-system correlation required manual joins in spreadsheets
  • Scaling risk: the existing infrastructure couldn't handle projected 5× traffic growth

Architecture & Technical Decisions

The core insight was to treat the platform as an event streaming system, not a polling dashboard. Every data source pushes events via webhooks or CDC (Change Data Capture) into a central Kafka-compatible queue. A Node.js processing layer normalises, enriches, and fans out events to two sinks:

  1. PostgreSQL + TimescaleDB for historical queries and aggregations
  2. Redis Streams for the live dashboard via WebSocket push

The frontend is a Next.js 15 App Router application using React Server Components for the heavy data tables and Client Components only where real-time updates are needed, keeping the JS bundle lean.

AI Co-Pilot

The AI layer runs on a scheduled LangChain chain that pulls the last 15-minute window of anomalies, runs them through GPT-4o with a custom system prompt that knows the customer's domain vocabulary, and posts the summary to Slack and the in-app notification centre.

// Simplified anomaly summary chain
const chain = RunnableSequence.from([
  anomalyFetcher,     // pulls last 15m events from Timescale
  contextEnricher,    // joins with customer metadata
  summaryPrompt,      // few-shot prompt with domain glossary
  new ChatOpenAI({ model: 'gpt-4o', temperature: 0.2 }),
  new StringOutputParser(),
]);

const summary = await chain.invoke({ windowMinutes: 15 });

Infrastructure

Everything runs on AWS: EKS for the application tier, RDS for PostgreSQL, ElastiCache for Redis, and CloudFront + S3 for static assets. GitHub Actions pipelines run tests, build Docker images, and roll out to EKS with zero-downtime blue-green deployments.

Customers

The platform replaced all six existing tools within 90 days of launch. The data team's morning report ritual went from 2.5 hours to zero — the AI co-pilot handles it overnight. MTTR on production incidents dropped from 47 minutes to 11 minutes because on-call engineers now see correlated context immediately rather than digging across dashboards.

Lessons Learned

The biggest surprise was how much prompt engineering mattered for the AI summaries. The first version used a generic prompt and produced vague, useless output. The breakthrough came when we embedded a customer-specific glossary (their internal product names, metric definitions, and known-good baselines) directly into the system prompt. Accuracy went from 40% useful to 90%+.

On the infrastructure side: starting with Kubernetes from day one proved valuable. We scaled from 3 nodes to 18 nodes during a Black Friday spike without any application changes — just kubectl scale.
